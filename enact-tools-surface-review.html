The three systems

at a glance

Each solves a different problem, and each is stronger than the others somewhere. The point of the comparison is not to copy a tool list — it is to see which mechanisms close gaps in enact-agent.

enact-agent baseline

zeroclaw fork · Rust · 93 built-ins · 226 ops
  • Rigorous three-axis model. Tier (Core 11 / Host 51 / Optional 31) × compilation (Always / External / OptIn) × catalog selector ([tools].optional). Neither competitor has anything close.
  • Strongest safety surface. Risk profiles, Landlock/Bubblewrap/Seatbelt/Docker sandboxes, approval gates, HMAC-signed tool receipts, default-deny MCP bundle scoping.
  • Unique runtime primitives. SOP engine with approval gates and resumable runs; 30+ channel adapters; A2A client; ACP; gateway + web dashboard.
  • The gap. Hooks are a Rust trait only — no user can write a hook. No structural code tools, no context tooling, no plan/goal mode.

oh-my-pi tool craft

Rust + TS monorepo · 30 built-ins + 3 hidden
  • Schema budget discipline. Tools are essential (13, always top-level) or discoverable (mounted behind xd:// devices, found by BM25). Unused schemas never enter the request.
  • Best hook system of the three. ~45 events, plain TypeScript files, .omp/hooks/pre|post/*.ts, with documented ordering, budgets and fail-closed semantics.
  • Richest code intelligence. ast_grep, ast_edit, lsp, debug, find — none of which enact-agent has.
  • Modes. Plan, Goal and Vibe. Plus approval tiers (read/write/exec) and restricted folders.

lean-ctx context engine

Rust · 51 public MCP tools · 12-tool lazy core
  • Already did the consolidation. 82 registry entry points → 35 canonical tools with typed action enums, shipped in 3.11.5. Legacy names survive as aliases.
  • Context as a first-class surface. compose, expand, compress, preload/prefetch, control overlays, budget radar.
  • Hook dialects for 11 hosts. Installs into Claude Code, Codex, Cursor, Windsurf, Gemini, Copilot, Kiro, Cline, Vibe, CodeBuddy, Qoder.
  • Two ideas worth stealing outright: mirror, don't grant (a rewrite may only approve what the host would have approved anyway) and never invalidate the cache prefix.

The headline finding

enact-agent already stores tool name + operation enum for all 226 operations — exactly the data model lean-ctx converged on. The 93 separate tool names are a presentation choice, not a structural constraint. Merging sibling families takes the surface to 83 tools with zero operations lost, and lean-ctx already proved the migration path (canonical + alias + telemetry before removal).

Hook systems compared

25 capabilities

The decisive difference: enact-agent's hooks are a Rust trait that only embedders can implement. oh-my-pi lets a user drop a TypeScript file in a folder; lean-ctx writes JSON or TOML into other agents' homes. Enact-agent is the only one of the three where a user cannot add a hook at all.

Blocker — no user-scriptable hooks

HooksConfig exposes exactly two fields (enabled, builtin) and BuiltinHooksConfig exactly two more (command_logger, webhook_audit). The WASM plugin system has capabilities Tool | Channel | Memory | Observer | Skill — no Hook. There is also no page in docs/book/src/ describing the hook system at all.

This is the single highest-leverage gap: the trait already models 18 events with correct cancel semantics, priority ordering and panic isolation. It needs an external surface, not a redesign.

One tool system across Codex & Claude Code

portability

Can one tool system be handed to both Codex and Claude Code? Yes — but not through a tool list. Every host speaks MCP, and each has its own instruction and policy conventions. The answer is a six-layer stack, and every layer has a proven reference implementation.

The one gap that blocks it: enact-agent cannot serve MCP

crates/zeroclaw-tools/src/ ships mcp_client.rs, mcp_transport.rs, mcp_tool.rs, mcp_deferred.rs — an MCP client. There is no server implementation anywhere in the tree: no ServerHandler, no list_tools/call_tool server side, no rmcp dependency. The protocol is hand-rolled on the client side.

This matters because Codex CLI has no server mode either — it is an MCP client and nothing more. Claude Code can serve its own tools (claude mcp serve); Codex cannot. So the only way to give Codex a tool set you control is to be an MCP server. That single missing mode is the whole difference between "enact-agent is one agent among many" and "enact-agent is the tool layer for every agent you use".

The six-layer stack

1 · Tools

Ship one MCP server

MCP is the only substrate every host speaks. Claude Code can even serve its own tools (claude mcp serve); Codex cannot — so an MCP server is the only way to give Codex a tool set you control.

enact-agent has no server mode today. This is the single highest-leverage change for the 'one system' goal.

2 · Tools, take two

Or offer a tool-injection API

jcode's Harness API exposes ConfigureTools { enabled, disabled, custom }: an external client registers its own tool implementations, the model calls them, and the runtime routes the call back down that client's connection. The custom tool is an execution adapter only — it never enters the shared registry, so hooks, telemetry, output limits and permission gates behave exactly as for built-ins.

This is the richer alternative to MCP when you own the host: the tool implementations stay in your process, and the runtime keeps its safety model intact.

3 · Schema budget

Expose search + call, not N schemas

jcode collapses MCP servers into a fixed mcp / mcp_search / mcp_call surface with a 32-reference cap and a 6 000-token result budget; providers with native deferred loading get defer_loading instead. Claude Code has MCP Tool Search; oh-my-pi uses xd:// devices + BM25.

enact-agent already has tool_search and mcp_deferred — extend the same idea to MCP servers.

4 · Behaviour

Per-host hook dialects

lean-ctx is the reference: 17 hook actions rendered into 11 host dialects, each installer writing that host's own config file. jcode keeps it simpler — eight external-program hooks, one command per event.

Ship Claude Code settings.json and Codex .codex/hooks.json installers. Do not invent a new hook format.

5 · Instructions

AGENTS.md + SKILL.md

Codex reads AGENTS.md natively. Claude Code reads AGENTS.md only when no CLAUDE.md exists (v2.1.277+), or you put an @path import on line 1 of CLAUDE.md, or set project instructions to claude-md-and-agents-md.

One AGENTS.md, one SKILL.md, imported by both. AGENTS.md is capped at 32 KiB by default. jcode, goose and oh-my-pi all already read these paths.

6 · Policy

Degrade to each host's own rules

Codex uses .rules files (allow / prompt / forbidden). Claude Code uses permissions in settings.json. They are not the same model and should not be unified.

A shared tool must respect the host's policy rather than assume it. enact-agent's availability-vs-authorization split maps cleanly onto this.

The pattern everyone converged on

Read the MCP column again: every serious system is an MCP client, and the ones that are also layers rather than agents — lean-ctx, Serena — are MCP servers. jcode, goose and oh-my-pi go further and deliberately read the host's own config: jcode reads Claude Code's live ~/.claude.json and one-time-imports Codex's ~/.codex/config.toml; goose imports Claude Desktop's MCP config on first run and reads ~/.claude/agents and ~/.claude/skills. The convention is portable even when the product is not.

jcode

1jehuang/jcode · Rust · MIT · ~21k★

The Rust harness you named. A single native binary built for running dozens of agents in parallel: ~19 ms time-to-first-input, megabytes per extra session, and a server-coordinated swarm that resolves the "agent B read a file agent A just edited" conflict for you.

★ The finding that answers "pass one tool system to them"

jcode's Harness API does more than drive a UI — it lets an external client inject a whole tool set. ApiRequest::ConfigureTools { session_id, tools: ToolConfiguration } carries enabled, disabled and custom: Vec<SessionToolDefinition>. A custom tool may even override a built-in of the same name. When the model calls it, the runtime emits a ToolCall event down that client's own connection and blocks; the client answers with a ToolResult (120 s deadline).

And it keeps the safety model intact: a custom tool is an execution adapter only, never installed in the shared registry — so hooks, telemetry, output limits and permission gates behave exactly as they do for built-ins. That is a complete, versioned contract for being the tool layer for a runtime you do not own.

Harness API tool injection

crates/jcode-harness-api · API_VERSION_MAJOR 1 / MINOR 11 · Unix socket, NDJSON
  • A stable, versioned boundary between the harness and ANY UI — TUI, desktop, web, scripts. Deliberately smaller than the internal jcode-protocol; only curated surface is public.
  • NDJSON, one JSON object per line. Every frame carries v (protocol major). Clients must ignore unknown fields and skip unknown event kinds.
  • Additive changes bump the minor version; breaking changes bump major and must be negotiated in the handshake.
  • The tool surface is reconfigurable at runtime — enable, disable and add custom tools per session, with session-scoped ownership so a stale client cannot remove a successor's policy.
  • There is also a TypeScript SDK (@1jehuang/jcode-sdk) with schema parity tests against the Rust side.

MCP config interop

crates/jcode-base/src/mcp/protocol.rs
  • Project precedence: .jcode/mcp.json → .mcp.json (Claude Code) → .claude/mcp.json. Later files override same-named servers.
  • Claude Code stays a live source — ~/.claude.json is read, never copied.
  • Codex is a one-time migration: imported from ~/.codex/config.toml [mcp_servers.*], and only while ~/.jcode/mcp.json does not exist.
  • Runnable wins: an existing working stdio server is kept over a lower-precedence definition, with a log line. A broken higher-precedence entry does not shadow a working one.

Schema budget & cache safety

crates/jcode-app-core/src/tool/mcp.rs · agent.rs
  • Three layers of mitigation. Providers with native deferred loading get defer_loading + cache_control; the rest get a fixed mcp / mcp_search / mcp_call surface (mcp_search and mcp_call are compatibility aliases, not model-visible); and tools that arrive late are announced in the transcript instead of the cached prefix.
  • mcp_search budgets — at most 32 tool references, under a 6 000-token result budget; a broad query trims descriptions first, then drops schemas for lower-ranked matches. Description-only matches are dropped once any name matches.
  • The tool list is locked after the first request so the provider prompt cache is not invalidated. MCP servers connect in the background; exactly one deliberate rebuild is allowed to pick them up — an intentional one-time cache miss, latched by a guard that is deliberately not re-armed.
  • Advertise-early: proxy tools are registered from the on-disk schema cache before connections settle, so the first locked snapshot already contains MCP tools and the cache miss can be avoided entirely.
  • AGENTS.md and the skills prompt section are snapshotted at session start, so tool writes cannot mutate the provider's cacheable prefix mid-session.

Swarm & self-development

crates/jcode-swarm-core · tool/communicate.rs
  • The swarm tool is communicate, exposed as swarm. It spawns and coordinates child agents, DMs one agent, broadcasts to all, or broadcasts to one repo.
  • File-change notices. When agent A edits a file agent B has read, B is notified and can inspect the diff before it conflicts.
  • Agents can spawn their own swarms — the main agent becomes a coordinator, spawned agents become workers.
  • Self-dev mode: an agent edits, builds, tests and reloads jcode's own binary mid-session.

jcode's external-program hooks

jcode keeps its hook system deliberately small: eight events, each a command string or an array of commands, executed directly rather than through a shell. Observers run in declaration order; gates run sequentially and the first block wins. Notably, post_tool_feedback feeds its stdout back into the tool result — that is how linters and checkers report findings straight to the model.

jcode's 35 built-in tools

ToolPurpose

What jcode is actually evidence for

jcode is not a competitor to enact-agent's tool surface — it is a second Rust agent runtime that happens to solve the same context-budget problem three more times over. Its value here is threefold: it proves the search + call pattern for MCP schemas works in production, it shows the config-interop precedence chain that lets one agent read another agent's MCP servers, and its Harness API is a clean model for the kind of stable, versioned, host-agnostic boundary enact-agent's ACP gateway is reaching for.

The most transferable single idea: read the hosts' configs instead of asking users to re-declare everything. Claude Code's ~/.claude.json, Codex's ~/.codex/config.toml, AGENTS.md, SKILL.md — those are the portable surfaces, and three of the four systems surveyed already read them.

Consolidation plan

93 → 83 tools

Sibling families that share a prefix and are always used together collapse into one tool with a typed action enum. All 244 operations survive — only the tool names change. This is exactly the migration lean-ctx ran between 3.11.4 and 3.11.5: canonical tool + typed actions + legacy aliases + telemetry before removal.

Why this matters beyond tidiness

lean-ctx states the case directly: "Agents currently receive too many overlapping MCP tool definitions. Large tool lists consume context, duplicate concepts across schemas, and make tool choice less reliable." oh-my-pi solves the same problem from the other end — 13 essential tools in the schema, everything else behind xd:// devices and BM25 discovery. enact-agent has deferred_builtin_tools and tool_search already, but the default catalog is still flat and large.

Sequencing, following lean-ctx's playbook

Step 1

no behaviour change
  • Introduce the canonical family tool with a typed action enum
  • Keep every old name registered as a thin alias that validates, translates, and delegates
  • Emit a one-time deprecation notice outside the tool result body

Step 2

default catalog
  • Make the merged surface the default in all_tools
  • Keep a compatibility profile that advertises the legacy aliases
  • Derive counts from the registry, never by hand

Step 3

proof
  • Table-driven test: every legacy name routes to exactly one canonical action
  • Assert alias and canonical results are byte-identical
  • Assert the default profile advertises the new count

Step 4

later
  • Remove aliases only in a major version
  • Only after telemetry shows no alias use for two release cycles
  • Publish the removal date and replacement route in release notes first

Bonus: one gateway instead of six SaaS tools

The 13 disabled OptIn adapters are all the same shape — a vendor API behind an auth model. lean-ctx replaces all of them with one ctx_provider gateway (GitHub, GitLab, Jira, Postgres, MCP bridges, custom REST). If enact-agent wants those integrations back later, that is one tool to build, not six.

Shipped. wait blocks on the durable task registry with a bounded timeout; learn records a lesson and can fold it into a named skill, and the skill tools are registered; approval tiers classify every tool read, write or exec and an operator may name a tier in auto_approve or always_ask; checkpoint and rewind mark and return to a point in the conversation; plan_mode puts the turn in plan mode, where only the read-tier tools run, and plan_execute asks the operator to let it act again. The three that need the conversation's history share one channel: the turn loop owns it, and the tools borrow it.
  • wait — await async results instead of polling (both competitors forbid polling).
  • learn + manage_skill — close the loop from a correction to a durable skill. enact-agent implements skill_manage but deliberately does not register it.
  • checkpoint + rewind — auto-include the pair; a one-sided tool strands the agent.
  • Plan mode — enact-agent has no plan/ask/research mode at all.
  • Approval tiers — read/write/exec, as a refinement of the existing risk profile and sandbox system.

What to leave alone

enact-agent's three-axis tier model, tool receipts, sandbox backends, approval gates, SOP engine, channel breadth, A2A client and per-agent MCP scoping have no counterpart in either competitor and are stronger than what oh-my-pi or lean-ctx offer. The recommendation is add and enhance, never replace. In particular, keep the availability-vs-authorization split (/// Availability only: callers must still enforce policy and prerequisites.) — it is the cleanest expression of the safety model in any of the three projects.
